# WORKFLOW.md --- 拉威尔《左手钢琴协奏曲》交互式导聆 MVP

> 本文是 Codex
> 的项目工作流与验收规范。目标是复用现有工具，先用一份真实作品跑通"PDF
> 识谱 → 离线音频对齐 → AI 辅助校验 → 人工修正 → 音乐分析 →
> 交互式导聆"的最小闭环。

## 0. 目标与核心原则

首个测试作品：Maurice Ravel, *Concerto pour la main
gauche*（拉威尔《左手钢琴协奏曲》）。

用户提供： - **MP3：必需**，作为真实录音。 - **PDF
总谱：必需**，是正式乐谱输入。 -
**MIDI：可选**，用于交叉验证节拍、音高和事件位置。没有 MIDI
时，系统仍必须能够基于 PDF 识谱结果继续工作。

原则： 1. PDF 是必需输入，MIDI 仅为辅助；禁止将 MIDI 设为必需依赖。 2.
以已录制音频的**离线全曲对齐**为主，不把实时跟谱作为核心流程。 3.
自动对齐结果必须可检查、可修正；不能把自动结果直接视为真值。 4.
音乐学分析与音频同步是两个独立工作流，最后才由播放器组合。 5.
先检查并复用成熟开源项目，避免重复造轮子。 6.
音频和乐谱默认只在本地处理；未经用户明确同意，不得上传到第三方服务。 7.
不伪造测试结果、文献、置信度或音乐学结论。

## 1. 开始前：检查工作区与技术选型

开始写代码前： 1.
检查当前仓库、目录、技术栈、README、依赖和测试；不要覆盖或重建已有项目。
2. 搜索工作区中的
MP3、PDF、MIDI；不要猜文件名。如果文件还没提供，搭建接口与测试骨架，并列出缺少的文件，不得声称已完成端到端测试。
3. 检查音频时长、采样率、声道，PDF 页数，MIDI 轨道/时长/拍号/速度事件。
4. 检查三个文件是否对应同一乐章和兼容版本；若不确定，明确报告。

先阅读官方文档、源码说明、许可证与已知限制，再选择工具。重点评估： -
Audiveris：PDF/图像乐谱 OMR，输出 MusicXML，并可人工检查和修正。 - Sync
Toolbox：https://github.com/meinard-mueller/synctoolbox - SSV
Alignment：https://github.com/Signature-Sound-Vienna/alignment -
Matchmaker：https://github.com/pymatchmaker/matchmaker（以在线 score
following 为主，仅作为对照，不默认选为主引擎） -
OpenVoicing：https://github.com/pjdoland/openvoicing（参考同步播放器、项目包与嵌入方式） -
Matchmaker Demo：https://github.com/pymatchmaker/matchmaker-demo（参考
PDF → OMR → 页面坐标映射，但不要把模拟在线跟谱当成离线全局对齐）

生成
`docs/archive/technical-spike.md`，比较各方案的输入格式、离线对齐能力、PDF/OMR
支持、许可、安装难度、限制和选型理由。若尚未实际验证，标记"待验证"。不要只凭项目名称推断功能。

## 2. 建议架构

先沿用当前仓库技术栈。若没有现成项目，采用： - 前端：React +
TypeScript + Vite。 - 处理层：本地 Python CLI 或本地 FastAPI，负责
OMR、音频特征提取和对齐工具调用。 - PDF 显示：保留原始 PDF
页面，并维护每个小节与页面坐标的映射。 - 结构化乐谱：MusicXML
或对齐引擎所需格式（必要时转换为 MEI）。 - 项目数据：本地 JSON/Markdown
文件；第一版不需要数据库、账号系统或云端存储。

前端负责播放、显示、跳转与校正交互；后端负责耗时计算；数据格式连接模块。不要把所有逻辑塞进一个
React 组件。

## 3. 工作流 A：输入审查

输入：MP3 + PDF + 可选 MIDI。

生成： -
`project.json`：作品信息、输入文件指纹、数据格式版本和处理状态。 -
`reports/input-audit.md`：输入文件检查、版本匹配情况、已知风险。

若 MIDI 缺失，显示"未提供，跳过 MIDI
交叉校验"，而不是报错。未经许可不要上传用户音频或乐谱。

## 4. 工作流 B：PDF 识谱（OMR）

1.  先尝试 Audiveris 或经过评估的替代方案，将 PDF
    转为可计算的乐谱表示，优先 MusicXML。
2.  **始终保留原始
    PDF**，播放器最终应能在原谱页面上高亮，不只展示重新排版的识谱结果。
3.  尽可能建立以下映射：
    -   PDF 页码；
    -   内部唯一小节 ID；
    -   原谱印刷小节编号（可能重复或缺失，不能作为唯一键）；
    -   小节在 PDF 页面上的矩形坐标；
    -   声部/谱表；
    -   对应的 MusicXML 小节和音符事件。
4.  生成
    `reports/omr-review.md`，列出未识别、疑似误识、编号不一致或坐标缺失的页面/小节。
5.  允许用户在原始 PDF
    上检查并修正识谱结果、编号和坐标；修正应可保存、撤销。
6.  不得假定 OMR
    对复杂管弦乐总谱完全准确。没有真实检测能力时，不要伪造置信度。

区分两项任务：OMR
负责把音符和节奏转成机器可读表示；页面定位负责知道每个小节在原 PDF
的哪个位置。二者都必须可检查。

## 5. 工作流 C：离线音频---乐谱对齐

目标是分析完整录音，输出全曲时间映射，而非实时逐帧跟谱。

1.  先确认候选引擎是否真正支持"预录音频 +
    符号化乐谱"的离线对齐，以及它要求 MusicXML、MEI、MIDI 还是其他输入。
2.  若不能直接使用 MusicXML，评估转换为 MEI
    或使用其他经过验证的离线对齐实现。
3.  有 MIDI 时，将其作为辅助参考；无 MIDI 时，必须基于 PDF 的 OMR
    结果继续。
4.  若尝试将识谱结果合成音频，再与 MP3 做音频---音频
    DTW，必须在真实素材上验证。合成音色与真实管弦乐的差异可能影响结果，不能默认有效。
5.  时间映射必须允许演奏速度非线性变化；不得按固定 BPM
    或按全曲时长平均分配小节。
6.  对华彩、相似乐句、主题再现、反复、弱起、停顿、跨页及可能的版本差异，检测歧义并允许人工处理。
7.  若算法输出的是拍或音符位置，转换成小节位置时必须考虑拍号变化、弱起和小节编号偏移，不得简单用固定拍数推算。

输出 `alignment.json`，至少包含： - 格式版本； - 录音与乐谱文件指纹； -
内部小节 ID； - 小节起止时间（秒）； - 算法、参数与可用的质量指标； -
异常标记； - 人工锚点及复核状态。

## 6. 工作流 D：AI 辅助校验 + 人工修正

AI 不应凭语言直觉宣布同步正确。它应发现异常、说明证据、建议检查位置。

检查： - 时间戳倒退、重复或超出音频长度； -
相邻小节的时间间隔异常或时间映射突跳； - MIDI（若有）与 OMR
的音高/节拍/事件冲突； - 音频特征是否支持候选乐谱位置； - PDF
页码、原谱小节编号与内部 ID 是否错位； -
反复、华彩或相似乐句是否可能造成多解。

要求： 1.
尽量使用独立证据交叉校验，不能让同一个模型生成结果后又凭直觉验证自己。
2. 每个异常记录小节、原因、依据和建议操作。 3.
区分"观测事实""算法推断""待确认假设"。 4. 用户能试听该小节前后音频、查看
PDF、移动时间锚点并保存。 5. 状态至少区分
`unreviewed`、`needs_review`、`verified`、`corrected`。模型分数不是未经校准的正确率。
6. 已确认的锚点不得在重新计算时被无提示覆盖。 7.
保存原值、新值、修改来源、时间和原因；支持局部重算，尽量不重跑全曲。

## 7. 工作流 E：独立音乐学研究与分析报告

分析报告必须能在同步完成前独立生成。不要把音乐分析直接写死在播放器代码中。

研究拉威尔《左手钢琴协奏曲》的学术论文、学位论文、专著和可靠音乐会导赏资料： -
优先原文、期刊/出版社页面、DOI 和大学论文库。 -
能读全文时核对相关章节；仅能查看摘要或元数据时明确标注。 -
记录作者、标题、年份、出版物、页码（如有）、DOI/稳定 URL、阅读状态。 -
区分乐谱可核验的事实、学者的分析解释和 AI 提出的待验证假设。 -
对曲式划分、动机来源、和声功能等存在歧义的地方保留不同解释，不强行给出唯一答案。 -
不为了覆盖每个小节而编造注释；一条注释可以覆盖一段小节。

分析范围： 1. 全曲曲式与段落结构； 2. 主题、动机与变形； 3.
调性、和声与节奏； 4. 配器、织体、音色和声部交接； 5.
华彩段及其结构功能； 6.
委约背景、历史语境和演奏实践（仅在有可靠依据时）。

输出： - `analysis/analysis.md`：完整独立报告； -
`analysis/bibliography.md`：文献清单、来源和阅读状态； -
`analysis/annotations.json`：播放器使用的结构化注释。

每条注释至少包含：
`annotation_id`、`start_measure_id`、`end_measure_id`、`category`、`title`、`text`、`evidence`、`source_ids`、`claim_type`、`review_status`。

`claim_type` 区分
`score_observation`、`scholarly_interpretation`、`hypothesis`。来源 ID
应能在 bibliography 中找到。不得编造引用或页码。

## 8. 工作流 F：React 导聆播放器

播放器只读取数据，不在播放时临时生成音乐学解释。

最小功能： - 本地 MP3 播放/暂停/跳转、当前时间显示； - 原始 PDF 显示； -
当前小节高亮； - 当前小节编号与前后小节导航； - 右侧显示对应分析注释； -
按类别筛选注释； - 点击注释跳到相关小节； - 显示同步复核状态； -
在校验模式试听局部音频、移动时间锚点并保存； -
导入、保存和导出项目数据。

播放时按音频当前时间查询 `alignment.json`，得到内部小节
ID，再通过小节---PDF 坐标映射绘制高亮，并查询 `annotations.json`
展示注释。不要把小节 ID、PDF 页码和时间戳混为一个字段。

## 9. 导出格式

设计版本化项目包（例如 `.mguide`，内部可用 ZIP），至少包含： -
`project.json` - `alignment.json` - `annotations.json` - 小节与 PDF
页面坐标映射 - `analysis/analysis.md` - `analysis/bibliography.md` -
校验与修正记录 - 来源、许可证、输入文件指纹

音频默认不随项目上传或公开；项目应标明需要用户提供哪一份录音。缺少依赖时显示清楚的提示，不能静默错配。

## 10. MVP 范围

### 必须完成

-   [ ] React + TypeScript 前端可启动。
-   [ ] 能选择并播放本地 MP3。
-   [ ] 能显示原始 PDF。
-   [ ] PDF → OMR 流程可运行，且结果可检查。
-   [ ] MIDI 是可选输入；缺少 MIDI 时流程仍可继续。
-   [ ] 有一种经过评估的离线全曲对齐方案。
-   [ ] 对齐结果可视化、可人工修正。
-   [ ] 当前播放位置能高亮 PDF 中对应小节。
-   [ ] 能显示独立生成的结构化分析注释。
-   [ ] 能保存、重新打开和导出项目数据。
-   [ ] 有明确的错误信息、异常报告和运行说明。

### 暂不做

-   账号系统、公共社区、云端音频托管；
-   实时跟谱；
-   "对所有乐谱都完美"的承诺；
-   未经复核的全自动学术分析；
-   默认上传文件到第三方服务。

## 11. 验收标准

### 输入与识谱

-   [ ] MP3、PDF 文件信息读取正常。
-   [ ] 不提供 MIDI 时流程仍可继续。
-   [ ] 文件版本不匹配时有警告。
-   [ ] 原始 PDF、内部小节 ID、原谱编号和页面坐标分开存储。
-   [ ] 识谱疑点可查看、可修正；未识别内容不会被默认为正确。

### 对齐与校验

-   [ ] 使用整首录音计算映射，不以固定 BPM 均分全曲。
-   [ ] 时间映射单调，时间戳处于有效范围。
-   [ ] 异常间隔和疑似错位能被报告。
-   [ ] 人工校正后，播放器高亮与播放位置一致。
-   [ ] 测试华彩/速度伸缩或相似乐句中的至少一个片段。
-   [ ] 保存后重新打开，映射和校正不会丢失。
-   [ ] 区分算法结果与人工确认结果。

### 音乐分析与集成

-   [ ] `analysis.md` 可独立于 `alignment.json` 生成和查看。
-   [ ] 注释有明确的小节范围和可追溯来源。
-   [ ] 未读全文的文献明确标注；不伪造引用、页码或分析确定性。
-   [ ] 最终完成一次端到端测试：先只用 MP3 + PDF，再加入 MIDI
    验证辅助校验路径。

## 12. Codex 执行顺序与交付

按阶段实施，每阶段运行测试并汇报，不要一次性生成大量未经验证的代码。

**第一阶段：** 检查工作区、输入文件和现有开源工具，产出
`docs/archive/technical-spike.md` 与 `reports/input-audit.md`（素材可用时）。

**第二阶段：** 确定数据格式，搭建前端与本地处理接口。

**第三阶段：** 实现 PDF 识谱与人工检查。

**第四阶段：** 集成离线对齐、异常报告和人工锚点校正。

**第五阶段：** 独立生成音乐分析报告与结构化注释。

**第六阶段：** 集成播放器、PDF 高亮、注释面板和项目导出。

每阶段必须报告：已完成、未完成、实际运行的测试、测试结果、已知限制和下一步。不得声称未运行的测试通过，也不得用虚构素材冒充真实测试。

最终交付至少包含： - `WORKFLOW.md` - `docs/archive/technical-spike.md` -
`reports/input-audit.md`（素材可用时） -
`reports/omr-review.md`（识谱后） - `analysis/analysis.md` -
`analysis/bibliography.md` - `analysis/annotations.json` -
`alignment.json` - 可启动的 React 前端与本地处理脚本 -
安装、运行与测试说明

**第一步请先审查现有工作区与工具，不要立即盲目编码。**
